# Local speech and conversation engines

Run `node server/index.mjs` from the app root after `npm install`. The HTTP server binds only to `127.0.0.1:8787`; set `SPEECH_PORT` to change the port. The frontend should proxy `/api` to that address.

Kokoro provides **text-to-speech (TTS)**, Whisper provides **speech-to-text (STT)**, and Qwen generates conversational replies. All inference runs locally; CPU is the default and an optional GPU bridge accelerates Qwen. No API key or remote inference service is used. The server does not access the microphone directly: the browser records only after the user starts a voice turn and submits a WAV file.

The backend uses the open-source `kokoro-js` package and Kokoro 82M v1 ONNX weights with `device: 'cpu'` and `dtype: 'q8'`. No GPU, external inference API, API key, or browser speech service is used. First startup requires internet to download the model (approximately 92 MB for the quantized weights plus small configuration files); later starts reuse `server/.cache/models`. The cache is configured through the actual `@huggingface/transformers` environment. Voices are bundled with the npm package. When the four required model files are cached, the backend disables remote model requests before startup. You can also force this mode with `SPEECH_OFFLINE=1`; an incomplete cache then fails clearly rather than downloading.

Conversation preparation additionally loads `Xenova/whisper-base.en` ONNX with Transformers.js (`device: 'cpu'`, `dtype: 'q8'`, approximately 79 MB cached) and `Qwen/Qwen2.5-1.5B-Instruct-GGUF` Q4_K_M through `node-llama-cpp` (approximately 1.12 GB). Whisper is English-only in this app. Whisper uses a separate Node process to isolate the native ONNX runtime from Kokoro on Windows; each resident Qwen model uses a worker, with caches at `server/.cache/stt` and `server/.cache/chat`. CPU Qwen uses `gpu: false` and zero GPU layers; GPU Qwen uses the detected backend with verified positive layer offloading. Both use a 6144-token context and at most six CPU threads. Its pinned GGUF download is verified by exact size and SHA-256 before loading. Neither conversation model is loaded by a health request.

Internet is needed for each model's initial download; complete caches support later offline use. `STT_OFFLINE=1` and `CHAT_OFFLINE=1` force their respective engines to use cached files and fail clearly if files are missing. These environment flags supplement `SPEECH_OFFLINE=1`. Model caches contain weights and configuration, not conversation transcripts.

The optional `quality` profile uses official `Qwen/Qwen3-4B-GGUF` Q4_K_M (2,497,280,256 bytes), also checked against a pinned revision and SHA-256. The default `fast` profile uses the 1.5B model. Qwen3's thinking budget is disabled for short spoken responses. Both models support the same CPU/default or optional GPU execution choice.

The third `hybrid` mode routes each request before generating an answer. A deterministic router uses the latest message and supplied recent conversation: short social turns use Fast; reasoning, technical work, plans, calculations and personal-memory requests use Quality. Contextual follow-ups can retain the stronger route. Memory summaries use Quality. Routing is a heuristic, not an estimate of confidence or a guarantee of correctness; manual Fast and Quality choices override it.

CPU Hybrid prepares both models when current free physical memory and, on Windows, commit headroom permit. Admission includes model/context budgets and a reserve for other work. When headroom is insufficient or cannot be checked reliably, one model stays resident and the required model loads on demand. A shared queue serializes model warm-ups, replies and summaries; keeping two models in memory does not start two simultaneous chat inferences. Optional second-model preparation can fail while leaving the healthy first model usable, with an explanation in health. A failed load required for a Quality-routed request surfaces an error instead of silently substituting Fast.

Health keeps `chat.profile: "hybrid"` while `selectedModel` identifies the actual answering model. `residentModels`, `residency` (`dual` or `single`) and `residencyReason` describe preparation and memory behavior. The browser keeps the selected mode and conversation memory stable across routes.

## Optional GPU bridge

CPU is the default after server startup. Detection probes locally installed `node-llama-cpp` binaries in a hidden, bounded subprocess with building and downloading disabled. Windows uses an existing CUDA runtime when compatible, otherwise Vulkan from the graphics driver. The verified RTX 4090 uses Vulkan. On machines with multiple adapters, the chosen Vulkan device is isolated through the GPU child's startup environment. Detection and switching do not install drivers, a toolkit, a global service or additional model files. Initial dependency installation is a separate step; npm packages can have their own install scripts.

The runtime requires compatible native binaries and drivers on the backend host. Only the Windows RTX 4090 setup has been verified end to end. Linux CUDA/Vulkan paths are present but unverified. Apple Silicon Metal detection is present, but the current default/return-to-CPU path requests a separate CPU binary that is not supplied by the inspected macOS ARM64 package; macOS needs compatibility work and testing. Intel Mac GPU operation is not established. No iOS, Android or browser WebGPU inference engine is included. The frontend and backend bind to loopback, so the delivered configuration also does not expose Milo to phones over a LAN. See the root [README](../README.md) for the compatibility matrix.

CPU residents use worker threads; the GPU resident uses a hidden child process so native allocations can be released on exit. Accelerated Hybrid keeps Fast on CPU and Quality on GPU when physical RAM and Windows commit headroom permit, with one GPU context and serialized inference. Manual Fast or Quality runs the chosen model on GPU. Changing modes replaces incompatible residents only after their termination is confirmed. Low-memory fallback loads the appropriate CPU or GPU resident on demand.

Device switching invalidates pending inference and retires the previous engine before loading a replacement. The latest ON/OFF request wins, including OFF during detection or loading. GPU load or inference failure restores CPU and reports that the interrupted turn needs retrying. A termination failure preserves the disposal barrier and prevents a potentially overlapping replacement until Milo is restarted. Supplied history and memory remain browser-owned and survive a device change.

Health's `chat.acceleration` contains `available`, `enabled`, `status` (`detecting`, `ready`, `switching`, `unavailable`, `error`), `backend`, `deviceName`, `message`, and a monotonically increasing `revision`. `enabled` represents the requested mode; `chat.device` and each `residentModels` entry describe actual execution. GPU residents also expose `gpuLayers`, `backend`, and `processId`. Hybrid residency remains `dual` when CPU Fast and GPU Quality are both resident. Other tabs use revision changes to cancel stale recording, playback and requests.

## API

- `POST /api/conversation/acceleration`: JSON `{ "enabled": true }` or `{ "enabled": false }`. Requires a boolean. Returns HTTP 202 with combined conversation health while the transition continues. Poll health for the completed state. The setting is shared by all tabs and resets to CPU after a server restart. This endpoint can interrupt active chat work; it does not clear browser history or memory.

- `GET /api/health`: JSON with `status` (`loading`, `ready`, or `error`), `message`, model/device/dtype, nullable numeric `progress`, supported voice IDs, and `queueDepth`. A warm-up inference must succeed before `ready` is reported.
- `POST /api/speech`: JSON `{ "text": "Hello there!", "voice": "af_heart", "speed": 1 }`. Text may contain 1–600 characters, speed 0.7–1.3, and voice is one of `af_heart`, `am_michael`, `bf_emma`. Returns mono 24 kHz PCM WAV, with `X-Audio-Duration` in seconds, `X-Generation-Ms`, and `X-Audio-Cached`.
- `GET /api/conversation/health`: JSON `{ "stt": { ... }, "chat": { ... }, "tts": { ... } }`. Each engine reports `status`, `model`, `device`, `dtype`, `message`, `progress`, and `offline`. Conversation engine status can be `unloaded`, `loading`, `ready`, or `error`; STT also reports `busy`, and chat reports `queueDepth`. This endpoint does not start model downloads.
- `POST /api/conversation/prepare`: send JSON with `profile: "fast"`, `"quality"` or `"hybrid"` (default `fast`). Starts or retries Whisper and the selected mode in the background and immediately returns HTTP 202 with combined health. Poll for readiness. A profile switch during loading/queued work returns 409. Preparation does not request microphone access or create conversation history.
- `POST /api/transcribe`: send the WAV bytes directly with `Content-Type: audio/wav` or `audio/x-wav`. Accepts only 16 kHz mono PCM16 WAV, 0.2–30 seconds, with a 1,000,000-byte HTTP body limit. The browser recorder uses a stricter 20-second limit. Returns JSON `{ "text": "Your transcribed words", "duration": 2.4, "transcriptionMs": 500 }`; duration is seconds. Invalid, empty, and near-silent recordings are rejected before model inference. The STT model initializes on demand if necessary.
- `POST /api/chat`: send JSON `{ "messages": [{ "role": "user", "content": "Hello Milo" }], "profile": "fast", "memory": { "summary": "", "facts": [] } }`. Profile and memory are optional. Accepts 1–12 messages, only `user` and `assistant` roles, ending in a user message. User messages are limited to 1,000 characters and assistant messages to 1,200; the HTTP body limit is 64,000 bytes. Returns JSON with `text`, `generationMs`, `model`, `device` and `profile`. Replies are bounded to 600 characters. Memory allows a 1,200-character summary and at most twelve nonempty facts of 180 characters each.
- `POST /api/chat/stream`: same request as `/api/chat`. Returns `application/x-ndjson`. Hybrid first emits `{ "type": "routing", "profile": "quality", "reason": "..." }`, then incremental `{ "type": "delta", "text": "..." }` events followed by `{ "type": "done", "text": "...", "generationMs": 1200, "model": "...", "device": "cpu", "profile": "quality", "mode": "hybrid" }`. The final `profile` identifies the model, while `mode` retains the requested mode. Concatenated deltas equal the final text. Errors after headers use `{ "type": "error", "code": "...", "message": "..." }`. Disconnecting cancels generation. The browser displays words progressively and buffers completed sentences for Kokoro; it never sends routing events or individual token deltas to TTS.
- `POST /api/chat/summary`: same profile/memory shape plus up to twelve older messages, which may end with an assistant. Returns `summary`, `generationMs`, `model`, `device` and `profile`. This is background continuity data; explicitly retained user facts and recent corrections take priority.
- Errors return `{ "error": "code", "message": "Readable explanation" }`: 400 invalid input, 403 rejected origin, 413 oversized body, 415 wrong content type, 422 no speech, 429 engine busy or queue full, 499 cancelled operation, 503 engine unavailable, 504 reply timeout, or 500 inference failure. A disconnected caller will not receive its cancellation response. HTTP 429 and 503 responses include `Retry-After: 3`.

JSON requests require `Content-Type: application/json`; speech and preparation requests have an 8,192-byte limit. The server accepts browser origins only from HTTP localhost or loopback hosts and returns `Cache-Control: no-store` for API responses. This is a local development server and should remain bound to loopback.

Speech inference is serialized with at most three active/queued unique requests. Repeated requests share in-flight work and a 24-entry/32 MB in-memory LRU cache. Text is split into short sentences/chunks before inference. The actual phoneme-token sequence is then checked with tokenizer truncation disabled: unusual numbers or acronyms that expand beyond 512 tokens including sentence-boundary tokens are rejected with `400 text_too_complex` and an explanation. No over-limit sequence is silently truncated. Cancelling browser playback does not interrupt an already running CPU speech inference; the result may complete into the cache.

STT allows one active transcription. Cancelling the request immediately rejects the caller and discards its eventual result, but native ONNX inference retains the CPU slot until it finishes. Chat allows one active reply and one waiting request. Cancellation signals the worker; if it cannot stop within 20 seconds the worker is terminated and later preparation reloads it. A running reply has a 90-second timeout; initial Qwen preparation has a 15-minute timeout.

The client releases microphone tracks before transcription or reply generation. In an explicitly started voice conversation with voice interruption enabled, it opens a new capture when playback begins. A sustained onset stops outgoing audio and promotes that capture into the next turn without dropping its pre-roll. Mute, End, mode changes and page exit release it. Typed turns never enable this monitoring by themselves. Browser echo cancellation is requested; acoustic echo performance depends on hardware and room conditions.

Each request rebuilds chat history from the supplied recent messages and memory, then clears it afterward. Resident model/session objects are reused; the backend does not persist audio, transcripts, or messages to disk. The browser retains explicit user facts and a rolling summary only in this tab. Cancelling, ending, or switching modes prevents stale results from being played. New chat and reload clear conversation memory; custom sentence preferences remain separate.

## Verify actual inference

With the server running, run `node server/verify.mjs`. It waits for engine readiness, requests real CPU-generated speech, checks the WAV format and non-silent waveform, verifies the cached repeat, and checks invalid-input rejection. It writes `server/verification/cpu-speech.wav` and `server/verification/report.json`.

After the model is cached, run `node server/verify-offline.mjs` to verify a fresh engine initialization and real CPU speech in a separate process with network `fetch` blocked. It asserts zero remote fetch attempts and writes `server/verification/offline-report.json` with the actual cache paths and sizes.

Run `node server/verify-stt.mjs` after the speech check has created its WAV fixture. It converts that fixture to the microphone WAV contract, performs real English transcription, checks invalid and silent audio, concurrent requests and cancellation, and repeats the check with `STT_OFFLINE=1`. Results and cache size are saved to `server/verification/stt-report.json`.

Run `node server/verify-chat.mjs` to verify both CPU profiles, incremental replies, summary/correction handling, isolation between supplied histories, cancellation recovery, and input validation. It writes `server/verification/chat-upgrades-fast-quality-report.json`. The report records Fast-model quality failures separately from transport checks; Quality checks assert the tested memory behavior. Set `CHAT_VERIFY_PROFILES=fast` to check only the smaller model. For an offline run after both models are cached:

```powershell
$env:CHAT_OFFLINE = '1'
node server/verify-chat.mjs
Remove-Item Env:CHAT_OFFLINE
```

The report includes `offlineMode: true`. These checks use generated fixtures or typed messages and do not record a physical microphone. A physical microphone conversation still needs manual verification.

With the local server running and the model caches available, run `node server/verify-hybrid.mjs` to check actual Hybrid routing, Fast → Quality → Fast continuity, supplied personal facts, exact streaming text, cancellation and recovery. It calls the running server instead of creating another model pool. Results are saved to `server/verification/hybrid-report.json`. The check leaves Hybrid selected.

With a detected compatible GPU, run `node server/verify-acceleration.mjs` against the running server. It compares the same Quality prompt and supplied facts on CPU and GPU, checks actual layer offloading, mixed Hybrid Fast CPU → Quality GPU → Fast CPU handoffs without reloads in dual mode, OFF during a GPU stream, and CPU recovery. It records optional NVIDIA memory observations and timings in `server/verification/acceleration-report.json`, then leaves acceleration off. It does not benchmark TTS/STT or end-to-end audible response time.
